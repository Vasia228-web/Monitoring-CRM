# Конфіги системи

Тут лежать усі пороги, списки й назви, які за промтом 11 не можна тримати в
коді: цілі швидкодії, ліміти, підписи знятих оголошень, довідник районів і ЖК
тощо. Тека в git — кожну зміну видно в історії, з датою й причиною.

## Правила

1. **Один файл — одна тема**, формат TOML (UTF-8):
   - `speed.toml` — Блок 2, швидкість сайту (вже є, але поки заготовка: код
     його ще не читає — див. шапку файлу);
   - згодом: `links.toml` (формати посилань джерел), `liveness.toml` (Блок 1),
     `seller.toml` і `privacy.toml` (Блок 3), `places/districts.toml`,
     `places/complexes.toml`, `places/rules.toml` (Блок 4), `lookup.toml`
     (Блок 5), `night.toml` (нічні роботи), `cycle.toml` (стелі кроків циклу).
   Файл з'являється разом із кодом, який його читає (або на крок раніше як
   заготовка — тоді в шапці файлу сказано, що він ще не діє).
2. **Біля кожного числа — звідки воно**, з посиланням на запис у
   `implementation-notes.md`: «Етап 0, D45», «рішення власника, D46 п. 6»,
   «план Блоку 2, D48», «розрахунок, D4x». Посилання — лише на те, що є в git:
   плани блоків лежать у тимчасовій теці й зникнуть, тому їхні числа разом із
   замірами переписано в журнал. Число без походження — не число, а здогад.
3. **У коді немає значень за замовчуванням.** Схема кожної теми — заморожений
   dataclass у `realty/configfiles.py`. Бракує ключа, є зайвий (наприклад, з
   одруківкою) або тип не той (`"300"` замість `300`, `1` замість `true`) —
   помилка `ConfigError`, а не тиха підстановка. Межі значень (мінімум,
   максимум, перелік дозволених) — теж у схемі.
4. **Хто як читає.** Сайт — `configfiles.get(тема)`: перечитує файл за часом
   зміни не частіше ніж раз на 60 с; якщо нова версія не проходить перевірку,
   лишається попередня чинна. Кроки циклу й нічні роботи — `configfiles.load(тема)`
   один раз на старті.
5. **Версія порогів.** У записи прогонів пишеться хеш перевірених значень (не
   коментарів і не написання: `30` і `30.0` у дробовому полі — та сама версія)
   саме тієї версії, що діє, а не файлу на диску: сайт — `get_with_hash(тема)`
   або `get_hash(тема)` (після зламаної правки там лишається хеш попередньої
   чинної), кроки циклу — `load_with_hash(тема)` на старті. `config_hash(тема)`
   хешує файл на диску зараз — лише для `config check` і перевірок.
6. **Перевірка:** `python cli.py config check` — кожен файл проходить свою
   схему, і для кожної схеми є файл; ненульовий код виходу при помилці.
   Запускається в процедурі розгортання ДО перезапуску служб — помилка скасовує
   розгортання (`deploy/fedora/install.sh` робить це сам). Те саме перевіряє
   тест `tests/test_configs_valid.py`.
7. **Перекриття** — лише змінна `REALTY_CONFIG_DIR` (для тестів і експериментів).
   Її читає й `.env`, тому перекриття не мовчить: попередження в журналі, а
   `config check` з ним не проходить без `--allow-override`. Локальних
   «*.local.toml» немає: неперевірений файл не можна переглянути в git.

## Що лишається, де було

- `.env` — секрети й перемикачі розгортання (паролі, токени, `DEDUP_RULES`,
  `PUBLIC_DOMAIN`, ліміти джерел).
- `realty/config.py` `SOURCES` — темп звичайного збору.
- Пріоритети й ліміти служб — у `deploy/fedora/systemd/*.service`: їх читає
  systemd, а не Python.

## Як змінити значення

Власник каже, що змінити → правка TOML окремим комітом (різницю видно в git) →
тести → розгортання між циклами: `git pull` → `.venv/bin/python cli.py config
check` (ненульовий код — зупинитись, служби не перезапускати) → перезапуск
служб → рядок у `implementation-notes.md` (Deviations) із «було/стало». На
Fedora файли руками не правимо.
