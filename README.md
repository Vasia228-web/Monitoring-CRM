# Агрегатор нерухомості — Івано-Франківськ

Збирає оголошення про **продаж квартир в Івано-Франківську** з п'яти джерел,
нормалізує їх в єдину схему й показує у веб-інтерфейсі з сортуванням і фільтрами.

## Швидкий старт

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/playwright install chromium      # потрібен лише для OLX
cp .env.example .env                       # за бажанням: ключ для LLM-фолбеку

.venv/bin/python cli.py scrape             # зібрати дані
.venv/bin/python cli.py serve              # http://127.0.0.1:8000
```

## Джерела та спосіб доступу

Кожне джерело перевірялося окремим скриптом у `probes/` до того, як потрапило
в пайплайн. Спосіб доступу обраний під конкретний сайт:

| Джерело | Доступ | Що дає |
|---|---|---|
| **DIM.RIA** | JSON `/node/searchEngine/v2/` + `/realty/data/{id}`, далі `__INITIAL_STATE__` сторінки | ціна, площа, кімнати, вулиця, район, поверх, опис, теги; зі сторінки — «стан квартири», тип нерухомості, рік будівництва |
| **LUN** | RSC-payload Next.js `/sale/if/flats` + картка rieltor.ua | ціна, $/м², кімнати, площа, рік, опис, `withoutRenovation`; зі сторінки-першоджерела — поле «Загальний стан квартири» |
| **OLX** | рендер у Chromium (Playwright): стрічка + сторінка оголошення | ціна, площа, дата; зі сторінки деталей — кімнати, поверх, вид об'єкта, опис |
| **flombu** | JSON:API `/uk/estate_deal_sales.json?filter[...]` | ціна, площа, адреса, координати |
| **blago** | статичний HTML каталогу планувань | ЖК, площа, кімнати; ціна лише як «від N грн/м²» |

Ідентифікатори, з'ясовані на етапі верифікації: DIM.RIA `state_id=15`, `city_id=15`;
LUN — код міста `if`.

### Обмеження, які варто знати

- **OLX** блокує HTTP-клієнти (CloudFront віддає 403), тому працює лише через
  реальний браузер. Це звичайний Chromium із локаллю `uk-UA` — без
  stealth-патчів і підміни відбитків.
- **flombu** ігнорує гео-фільтр і повертає всю область, тому остаточний відбір
  міських лотів робиться на нашому боці; корисних записів на сторінку небагато.
- **blago** не має реальної пагінації (`/plannings/page/N/` віддає той самий
  набір), тому обходимо тематичні розділи каталогу й дедуплікуємо. Ціни за
  об'єкт забудовник не публікує — загальна ціна рахується як
  `площа × грн/м²` і позначається прапорцем `price_estimated`.
- **LUN**: розділ новобудов — це каталог ЖК без даних по квартирах, тому
  первинний ринок беремо з DIM.RIA, flombu і blago.

## Схема даних

`realty/models.py`, таблиця `listings` (SQLite через SQLAlchemy):

| Поле | Опис |
|---|---|
| `price`, `currency` | ціна у валюті оголошення |
| `price_usd`, `price_uah` | єдина шкала для сортування (курс НБУ, з резервом у `.env`) |
| `rooms`, `area_total` | кімнати, загальна площа |
| `price_per_sqm` | $/м² — з джерела або розрахунок |
| `location`, `district` | адреса/район в Івано-Франківську |
| `published_at` | дата публікації |
| `market_type` | `primary` (новобудова) / `secondary` / `unknown` |
| `condition` | `renovated` (з ремонтом) / `needs_repair` (без ремонту) / `unknown` |
| `original_url` | пряме посилання на оголошення |
| `source`, `external_id` | джерело й ключ дедуплікації |
| `price_estimated`, `detail_enriched`, `llm_extracted` | прапорці якості даних: ціна є оцінкою; поля дібрані зі сторінки деталей; поля дібрані моделлю |

Ключ ідентичності — пара `(source, external_id)`; повторний прогін оновлює
наявні записи, а не дублює їх.

> **`original_url` навмисно не унікальний.** LUN — агрегатор і віддає посилання
> на інші сайти, зокрема на olx.ua, тож те саме посилання законно приходить від
> двох джерел. Поки на колонці стояв `UNIQUE`, повний збір LUN падав на
> конфлікті. Однакові URL зводить дедуплікація — це найнадійніший з її сигналів.

Записи пишуться пачками по 200, і **кожен запис ізольований точкою
збереження**. Без цього одна помилка цілісності отруювала транзакцію: усі
наступні `upsert` падали, підсумковий `commit` теж, і пакет відкочувався
цілком — на повному прогоні так було втрачено понад 5 000 зібраних оголошень
LUN через єдиний конфлікт посилань.

### Історія цін

Таблиця `price_events` фіксує зміну ціни в оголошенні — і лише зміну:
повторний прогін із тією самою ціною запису не створює, інакше історія
перетворилась би на журнал прогонів. Для майстер-запису історія всіх його
оголошень зводиться в одну: `/api/properties/{id}/prices`.

## Архітектура

```
cli.py                 scrape / serve / stats
realty/
  config.py            гео-константи, темп запитів, налаштування джерел
  fetcher.py           HTTP-клієнт (ретраї, кеш, ліміт темпу) + рендер у Chromium
  normalize.py         парсери ціни/площі/кімнат/дат, класифікатори, гео-фільтр
  llm.py               резервне вилучення через Claude API (structured output)
  sources/             по модулю на джерело, спільний контракт у base.py
  pipeline.py          збір -> LLM-фолбек -> upsert
  web/                 FastAPI + Jinja2
probes/                ізольовані скрипти верифікації джерел
tests/                 регресійні тести парсерів
```

### Три рівні вилучення

Резервні рівні вмикаються за прогалинами, і прогалини поділені на два види
(`Pipeline._gaps`):

- **критичні** — `price`, `rooms`, `area_total`. Запускають обидва резервні рівні,
  включно з платним викликом моделі.
- **бажані** — `market_type`, `condition`. Запускають лише рівень 2: зазирнути
  на сторінку оголошення дешево, а платити за них викликом моделі не варто.

Сторінка оголошення завантажується щонайбільше один раз і обслуговує обидва
резервні рівні.

1. **Стрічка джерела** — JSON-ендпоінти (DIM.RIA, flombu), вбудований payload
   (LUN) або картки списку (OLX, blago). Прив'язуємось до стабільних
   атрибутів (`data-testid`, `data-cy`) і до форми тексту, а не до
   згенерованих класів на кшталт `css-13vv2xi`.
2. **Сторінка деталей, детерміновано** — хук `BaseSource.enrich`:
   - **OLX** (`realty/sources/olx.py`) — сторінка оголошення віддає параметри
     списком «Ключ: Значення» (`Кількість кімнат: 3 кімнати`,
     `Вид об'єкта: Новобудова`, `Поверх: 1`), серед них — власне поле
     **«Ремонт»** із семи значень, плюс опис.
   - **flombu** (`realty/sources/flombu.py`) — опису немає ні в стрічці, ні в
     JSON-версії сторінки, зате він є в HTML: блок одразу після заголовка «Опис».
   - **LUN** (`realty/sources/rieltor.py`) — LUN агрегатор, і його
     `original_url` веде на сайт-першоджерело, майже завжди rieltor.ua
     (143 зі 144 зібраних оголошень). Картка rieltor.ua має пряме поле
     **«Загальний стан квартири»**, якого в payload LUN немає взагалі.
     `rieltor.py` — не джерело: власної стрічки ми там не читаємо, це лише
   - **DIM.RIA** (`realty/sources/domria.py`) — особливий випадок: рівень 2 йде
     не по нові поля, а по ті самі, яких **не віддає API**. JSON-ендпоінт
     `realty/data/{id}` повертає `characteristics_values` порожнім, а
     HTML-сторінка несе ті самі характеристики вже з людськими назвами — у
     `window.__INITIAL_STATE__`. Там лежить пряме поле
     **«стан квартири»** (дизайнерський ремонт / косметичний / хороший /
     потребує ремонту) і мітка ринку в `mainCharacteristics`.

   `enrich` не має лише **blago** — каталог планувань забудовника, де сторінка
   деталей нових полів не додає.

   > **Пастка DIM.RIA.** Поруч зі станом квартири лежить група
   > «Зовнішня обробка» зі значенням «без оздоблення» — це про **фасад**, а не
   > про квартиру. Без перевірки назви групи такі оголошення хибно ставали б
   > «без ремонту», тож `parse_detail` читає стан лише з групи
   > «Характеристика приміщення». Це зафіксовано окремим тестом.

   > **Особливість payload LUN.** Довгі описи RSC-потік зберігає окремими
   > записами, а в об'єкті оголошення лишає посилання: `"text": "$31"`.
   > Записи йдуть впритул, без переносу рядка (`31:T7e7,<текст>32:T807,<...>`),
   > а їх довжина вказана **в байтах UTF-8**. `resolve_text_rows` розбирає їх
   > послідовно; без цього опис губився приблизно в чверті оголошень LUN.
3. **LLM-фолбек** — якщо критичних полів бракує і після сторінки деталей,
   очищений текст іде в Claude API (`realty/llm.py`). Модель **доповнює лише
   порожні поля** й ніколи не перезаписує те, що вже розібрав парсер.

   Рівень платний, тому підпорядкований економії:

   | правило | як реалізовано |
   |---|---|
   | тільки як резерв | тригер — відсутність `price` / `rooms` / `area_total`; стан і ринок виклику не варті |
   | найдешевша модель | `claude-haiku-4-5` ($1/$5 за млн токенів); Sonnet/Opus для парсингу заборонені |
   | ніякого HTML у запиті | `clean_html` вирізає `script`, `style`, `svg`, шапку, футер, меню, банери — 380 КБ сторінки стискаються до ~2 500 символів (150×) |
   | стеля обсягу | `LLM_MAX_CHARS=2500`; при переповненні лишаються рядки з ціною, площею, кімнатами та опис, а не перші N символів поспіль |
   | стисла відповідь | строга схема (`output_format`), `max_tokens=512`, жодного Markdown |
   | без повторів | сторінка, яка вже дала помилку, у межах прогону не запитується вдруге |
   | стеля викликів | `LLM_MAX_CALLS=25` на прогін |
   | видимість витрат | у звіті: кількість викликів, токени й вартість у доларах |

   Без ключа Anthropic рівень вимикається **до** першого мережевого запиту,
   а не після нього.

   На зібраних 573 оголошеннях модель знадобилася **один раз** — для пентхауса,
   де OLX не заповнив кількість кімнат: 2 267 вхідних + 51 вихідний токен,
   $0.0025. Решта 99.8% розібрано безкоштовно.

Сторінка деталей завантажується тільки тоді, коли в записі є прогалина **і**
джерело має чим її закрити: для `blago`, який `enrich` не перевизначає, без
ключа Anthropic жодного зайвого запиту не буде (перевірено тестом).

### Звідки береться `condition`

Порядок правил у `classify_condition` (`realty/normalize.py`):

1. **Заперечення першими** — «без ремонту», «сирець», «чорнова обробка».
   Інакше «без ремонту» спрацювало б як «ремонт».
2. **Ознаки готовності** — «євроремонт», «заїжджай і живи», а також теги RIA
   «З обробкою» й «Обставлена».
3. **Некеровані ЖК** — якщо ринок первинний і в тексті сказано, що будинок ще
   не зданий («здача заявлена в 1 кварталі 2028»), стан вважається «без
   ремонту»: квартири фізично ще немає. Правило вмикається лише разом із
   підказкою про ринок і поступається явній згадці ремонту.

Якщо сайт має **власне поле стану**, воно має пріоритет над усіма правилами
вище: пряме значення точніше за здогад із тексту. Такі поля є у трьох джерел,
і всі три словники взяті з самих сайтів, а не вгадані:

| джерело | поле | значення |
|---|---|---|
| OLX | «Ремонт» | авторський проект · євроремонт · косметичний ремонт · житловий стан · після будівельників · під чистову обробку · аварійний стан |
| DIM.RIA | «стан квартири» | дизайнерський ремонт · євроремонт · косметичний · хороший · потребує ремонту |
| rieltor.ua | «Загальний стан квартири» | з ремонтом · без ремонту · частковий ремонт |

Жодне зі значень OLX не ловиться текстовими шаблонами: «Житловий стан» не
містить слова «ремонт», а «Під чистову обробку» — це протилежність «чорновій
обробці», хоч формулювання й схожі.

Значення rieltor.ua «Частковий ремонт» свідомо не мапиться: у бінарній схемі
воно не є ні готовністю до проживання, ні сирцем, тож лишається `unknown`.

Те, що не потрапило під жодне правило, лишається `unknown` — у веб-інтерфейсі
це окреме значення фільтра. Здогади сюди не пишемо.

### Режими збору

| режим | коли | що робить |
|---|---|---|
| `fresh` (типово) | щоденний фон | іде по найновіших; джерела з датним сортуванням зупиняються на першій сторінці без новинок |
| `full` | одноразово | знімає стелю глибини, зберігає прогрес посторінково |

Рання зупинка дозволена лише **DIM.RIA** і **OLX**: перший типово віддає
спадний `realty_id`, другому явно передаємо `search[order]=created_at:desc`.
**LUN** робочого параметра сортування за датою не має — у його стрічці новинки
перемішані зі старими, тож рання зупинка там була б хибною і працює лише
стеля сторінок.

### Фоновий розклад

```bash
python cli.py schedule install --hours 3   # launchd, кожні 3 години
python cli.py schedule status              # стан, останній код виходу, помилки
python cli.py schedule uninstall
python cli.py schedule cron                # рядок для crontab
python cli.py schedule worker              # вбудований воркер, без launchd
```

> **Проєкт має лежати поза `~/Desktop`, `~/Documents` і `~/Downloads`.**
> macOS (TCC) не пускає туди фонові агенти launchd без Full Disk Access:
> агент падає з `Operation not permitted` ще до запуску скрипта, причому
> мовчки — власний лог агента теж опиняється в закритому каталозі, тому він
> пишеться в `~/Library/Logs/realty/`. `schedule install` перевіряє
> розташування й попереджає. Саме через це проєкт живе в `~/realty`.
> Якщо перенести його не можна, лишається `schedule worker` — він успадковує
> права термінала, з якого запущений, але не переживає перезавантаження.

### Повний історичний збір

```bash
.venv/bin/python scripts/full_scrape.py --dry-run   # план і оцінка часу
.venv/bin/python scripts/full_scrape.py             # повний прогін
.venv/bin/python scripts/full_scrape.py --reset     # почати з нуля
```

Прогрес пишеться в `data/full_scrape_state.json` **на кожній сторінці**, тож
перерваний прогін продовжується з тієї сторінки, де зупинився. `Ctrl+C`
завершує поточне джерело й зберігає стан; повторний — виходить негайно.

### Міжплатформна дедуплікація

```bash
python cli.py dedup --dry-run   # порахувати без запису
python cli.py dedup             # звести в майстер-записи
```

Одна квартира на кількох сайтах стає одним записом `Property` з масивом
посилань на всі оригінали (`/api/properties`) і спільною історією цін
(`/api/properties/{id}/prices`).

**Чому не жорсткий складений ключ.** Адресу з вулицею та будинком дають лише
DIM.RIA і LUN; OLX і flombu вказують саме місто, blago — назву ЖК. Тому пари
оцінюються за сукупністю ознак, а об'єднання відбувається при `score ≥ 6`:

| ознака | вага |
|---|---|
| різна кількість кімнат, площа поза допуском 0.6 м², різний поверх, різні вулиці | заборона |
| збіг вулиці | +3, ще +3 за спільний номер будинку (−6 за різні) |
| площа з точністю 0.3 м² | +2 |
| ціна в межах 3% | +3 (до 10% — +1, понад 25% — −2) |
| збіг району | +1 |

Три знахідки, які визначили алгоритм:

1. **Порядок слів різний.** LUN пише «Героїв Миколаєва вул., Будинок 3,
   Тисменицька», DIM.RIA — «вул. Героїв Миколаєва, 3». Адреси порівнюються як
   набори слів із перетином ≥ 0.65, а не рядками.
2. **Номер будинку не один.** «Княгинин, 44 корпус 13» і «Будинок 13» — той
   самий будинок. Тому з адреси беруться **всі** числа, а збігом вважається
   непорожній перетин множин.
3. **Безадресне оголошення робить місток.** Запис OLX без адреси однаково
   схожий на дві квартири на різних вулицях, і наївне об'єднання пар
   транзитивно зливало Івасюка 86 з Височана 18. Тому спершу будуються якорі
   з адресних оголошень, і лише потім безадресні приєднуються — кожне
   щонайбільше до одного якоря.

### Дозбір наявних записів

Коли новий рівень вилучення з'являється після того, як частину оголошень уже
зібрано, у стрічці джерела їх може вже не бути. Для цього є окрема команда:

```bash
python cli.py backfill              # усі джерела
python cli.py backfill --sources olx --limit 100
```

Вона бере з бази записи з прогалинами — критичними або бажаними — і проганяє
їх через рівні 2-3.

## Веб-інтерфейс

Мінімалістичний макет у «редакційному» дусі: жодних вкладених карток і рамок —
структуру тримають волосяні лінії, відступи й типографіка. Один акцентний
колір працює тільки на посиланнях і активному сортуванні; стан житла
позначається крапкою, а не яскравим бейджем.

- **Зведення** показує **медіани**, а не середні: кілька дорогих об'єктів
  зміщують середнє так, що воно перестає описувати типову пропозицію
  (у зібраних даних середнє за м² — $1301, медіана — $1134).
- **Фільтри застосовуються одразу**, без кнопки. Стан житла — головний фільтр
  за ТЗ — винесено в сегментований перемикач. Порожні поля не потрапляють
  в адресу, тож посилання лишається читабельним:
  `?condition=needs_repair&sort=date_desc`.
- **Сортування** — за ціною, кімнатами, $/м² і датою; активний напрямок
  підсвічено в заголовку колонки.
- **Ціна за м²** супроводжується відхиленням від медіани (`+56% від медіани`),
  якщо воно перевищує 10% — так одразу видно, де оголошення випадає з ринку.
  Це ж робить очевидними й аномалії в даних самих джерел.
- **Дати** відносні: «сьогодні», «3 дні тому», «2 тиж. тому».
- **`Не вказано`** — окреме значення, а не порожнє місце: під таблицею
  пояснено, що продавець не заповнив це поле в джерелі.
- **Адаптивність**: на вузькому екрані рядки таблиці стають картками
  (ціна і $/м² зверху, далі адреса, параметри, стан).
- **Світла й темна теми** — за системним налаштуванням.
- JSON тих самих даних: `/api/listings`, зведення — `/api/stats`,
  схема — `/api/docs`.

## Що показує список

Одна квартира — **один рядок**. Оголошення про той самий об'єкт із різних
майданчиків зведені разом; решту видно на сторінці об'єкта. Без цього та сама
квартира стояла у видачі тричі — з OLX, LUN і DOM.RIA, — і виглядало це як
провал дедуплікації, хоч вона спрацювала. 15 200 рядків → 6 765 об'єктів.
Перемикач «показати всі оголошення» лишає старий вигляд доступним.

**Перелистування** замість стелі в 500 записів. Нарізає база, а не пам'ять.
Розмір сторінки 50 / 100 / 200, поле переходу на номер, згорнута середина
(`1 … 4 5 6 … 310`). Номер сторінки, фільтри й сортування — в адресі, тож
працює кнопка «назад» і посилання можна передати.

Сортування **завжди має другий, унікальний ключ**. У базі підряд стоять
кілька записів по $146 500; без цього ключа порядок усередині такої групи не
визначений, і при перелистуванні одні записи з'являлись би двічі, інші
зникали. Тест проходить усі сторінки поспіль і звіряє, що жоден `id` не
повторився й жодного не бракує.

**Стан фільтрів переживає перехід між вкладками.** Посилання у верхній
навігації несуть поточну вибірку з собою — раніше вони вели на голий `/`, і
клік по вкладці починав усе спочатку. Кнопка скидання завжди видима й
лишає людину на тій самій сторінці.

### Кнопка «дані не збігаються»

На картці об'єкта, одне натискання без форми. Скарги накопичуються й видно їх
на `/status` у розрізі полів. По цьому списку видно, які правила класифікації
ламаються найчастіше — це найдешевше джерело для наступних виправлень, бо
показує людина, яка справді відкрила оголошення.

Оголошення, на яке поскаржились, піднімається в черзі перевірок. І сама
картка при відкритті перевіряє свої оголошення одразу — один запит у момент,
коли він справді потрібен.

## Аналітика

Шар над зібраною базою: нічого не збирає, рахує по тому, що вже є. Головне
рішення тут — **що рахувати відмовляємось**, і чому.

### Що показано в інвентаризації

`python cli.py analytics inventory` міряє, які графіки взагалі можна побудувати
чесно. Станом на перший прогін:

| | |
|---|---|
| Унікальних майстер-об'єктів | 7417 |
| Глибина власної історії цін | 3.8 дня |
| Об'єктів зі справжньою зміною ціни | 465 |
| Знято з продажу | 2 із 16191 |
| Сегментів із вибіркою ≥30 | 27 із 37 (98% бази) |

Ці п'ять чисел і вирішують, що працює, а що заблоковано.

### Сторінка об'єкта

Головна відповідь — **на скільки відсотків дорожче або дешевше за схожі**.
Порівняння йде по драбині: район + смуга площі → смуга площі → сегмент →
кімнатність. Спускаємось, доки не набереться поріг вибірки, і підписуємо, на
якому рівні порівняли.

Смуга площі потрібна тому, що ціна за м² залежить від розміру квартири навіть
усередині однієї кімнатності. Напрямок ефекту виміряно, а не припущено: у
однокімнатних **більші** квартири дорожчі за м² на 14.8% між крайніми
квартилями площі — протилежно до звичного уявлення.

Ціна й ціна за м² на сторінці виводяться з однієї величини — медіани цін
склеєних оголошень. Майстер-запис зберігає мінімальну ціну окремо від
найчастішої ціни за м², і разом вони не сходяться.

**Історія ціни** рахує зміни всередині одного оголошення. Поява того самого
об'єкта на другому майданчику дає новий запис із власною базовою ціною — це
не зміна ціни продавцем. Без цієї межі об'єкт із восьми склеєних оголошень
показував би «9 змін ціни», яких не було.

Якщо ціни майданчиків розходяться більше ніж на 25%, сторінка радить
перечитати склейку: така різниця частіше означає дві різні квартири, ніж
різні прайси на одну.

### Що заблоковано і до якої дати

Порожній блок із числом — штатний стан, а не помилка.

| Блок | Чому | Коли |
|---|---|---|
| Динаміка медіани в часі | 3.8 дня спостережень | ~06.12.2026 |
| Прогноз (сегмент і об'єкт) | бектест неможливий | ~11.01.2027, горизонт 1.4 міс. |
| Строк продажу, ліквідність | 2 зникнення з потрібних 50 | залежить від темпу перевірки |
| Сезонність | потрібні 2 річні цикли | ~05.09.2028 |

**Горизонт прогнозу рахується, а не задається**: стеля — третина спостереженого
періоду. Тому прогноз на 36 місяців не з'явиться і після цих дат; з піврічної
історії чесний максимум — два місяці. `python cli.py analytics forecast`
показує зворотний відлік, і той самий рядок пише планувальник у лог.

Дата публікації оголошення **не годиться** за вісь часу: у базі є оголошення
2022 року, але ми бачимо лише ті старі, що досі висять, — тобто саме
непродані. Тренд по них був би трендом відбору. Цифра перекосу: 61% оголошень
молодші за 90 днів, старших за рік — 3.1%.

### Порівняння майданчиків

Тільки в межах однакового сегмента. Наївна медіана по джерелу міряє асортимент:
частка новобудов — 72% у DOM.RIA, 63% у LUN, 91% в OLX, 100% у blago. На
зіставних сегментах картина інша — у 1к новобудовах з ремонтом три джерела
розходяться на 1.9%, а не на 11%. Джерело без жодного сегмента з достатньою
вибіркою (flombu, 26 оголошень) названо окремо, а не втоплено в середньому.

### Строк продажу

Реалізований оцінкою Каплана—Меєра — вона враховує об'єкти, які ще не продані.
Перевірено на синтетиці з відомою відповіддю: при 59% незавершених спостережень
метод дає 85 днів проти справжніх 90, а проста медіана по знятих — 33 дні,
тобто занижує майже втричі.

Крива не показується, доки зникнень менше 50. Темп їх накопичення **міряється**
по фактичних позначках перевірки, а не береться з налаштувань: розмір порції
і реальна швидкість — різні речі.

Окремо підписано на самому блоці: зникнення оголошення не дорівнює продажу.

### Пороги

Усі в `realty/analytics/settings.py`, зберігаються в
`data/analytics_settings.json` — правити можна без зміни коду.

| Поріг | Значення | Чому саме так |
|---|---|---|
| `min_sample` | 30 | 27 із 37 комбінацій набирають його й покривають 98% бази |
| `outlier_k` | 3.0 | «далекі викиди» Тьюкі в логарифмі: прибирає одруківки, не чіпає дорогі квартири |
| `area_band_pct` | 0.15 | виміряний вплив площі на ціну за м² |
| `forecast_horizon_ratio` | 1/3 | стеля екстраполяції від спостереженого періоду |
| `survival_min_events` | 50 | нижче крива виживання — пласка лінія |
| `merge_suspect_spread` | 25% | вище — підозра на склейку двох різних квартир |

Викиди відсікаються **до** агрегації. Для віку оголошення межа одностороння:
нуль днів — законне значення, а не одруківка, і двостороннє відсікання
викидало б саме найсвіжіші записи.

## Контроль якості даних

Шар над пайплайном: жоден запис не потрапляє у видачу, доки не пройшов
перевірку. Статус зберігається полем `quality_status` — `pending` (щойно
зібраний, невидимий), `ok`, `review`, `rejected`. **Нічого не видаляється**:
відхилений запис лишається в базі з причиною.

```bash
python cli.py quality diagnose      # що не так із даними просто зараз
python cli.py quality thresholds    # чинні пороги
python cli.py quality revalidate    # прогнати базу під поточними правилами
python cli.py quality audit         # аудит дедуплікації
python cli.py quality daily|weekly|monthly
```

### Пороги рахуються з даних, а не вписані в код

Огорожі Тьюкі в логарифмічному просторі — робастний спосіб для скошених
розподілів, яким і є ціна нерухомості. Два рівні, бо ціна помилки різна:

| | коефіцієнт | що означає | частка бази |
|---|---|---|---|
| перегляд | k = 1.5 | підозріло, чекає людину | ~1.2% |
| відхилення | k = 3.0 | зламані дані, у видачу не пускаємо | ~0.3% |

Перераховуються щотижневою рутиною, тож рухаються разом із ринком.
Поточні значення — у `data/quality_thresholds.json`.

### Що перевіряється

- `price`, `rooms`, `location`, `original_url` — без них запис не проходить;
- ціна, ціна за м² і площа — у межах порогів вище;
- **різкий стрибок ціни** (≥70% за одне оновлення) не перезаписує історію
  мовчки, а йде на перегляд. Реальний випадок із бази: оголошення стрибнуло
  з $1 504 до $77 967;
- відповідь LLM перевіряється на адекватність **до** того, як потрапить у
  карантин: схема гарантує типи, але ціна 0 чи 40 кімнат формально валідні.

### Ескалація

Якщо в одному прогоні джерела відхилено понад 20% записів (і пакет не
дрібніший за 20), пакет **не приймається взагалі** — швидше зламався парсер,
ніж джерело раптом почало публікувати сміття. Формується звіт із прикладами
й причинами, а не тихе відкидання.

### Рутини

Розклад сам обирає глибину: першого числа місяця — повна звірка, у понеділок —
аудит дедуплікації з перерахунком порогів, решту днів — легка щоденна.

### Що показав перший прогін по реальній базі

| | до | після |
|---|---|---|
| записів без перевірки | 15 276 | 0 |
| чистих | — | 15 041 (98,46%) |
| на перегляді | — | 186 (1,22%) |
| відхилено | — | 49 (0,32%) |

Аудит дедуплікації знайшов 60 суперечливих майстер-записів; найгірший — 23

## Актуальність оголошень

Без цього база лише зростає: продана квартира лишається в ній назавжди як
активна, і статистика рахується по суміші живих і знятих оголошень.

```bash
python cli.py snapshot                      # позначити зниклих із переліку (absent_since)
python cli.py verify                        # прогін перевірки ярусами (крок циклу)
python cli.py verify --sources domria,olx
python cli.py liveness plan                 # які ключі піде перевіряти наступний прогін
python cli.py liveness fuse status          # запобіжник; fuse clear --source domria — зняти
python cli.py night --dry-run               # план нічного вікна: ключі × темп = тривалість
python cli.py liveness report               # підсумки останньої ночі по сайтах, до/після
```

Механізмів два, і в них різні ролі. **Різниця списків** дешево й широко
позначає зниклих із повного переліку джерела (`listings.absent_since`) — це лише
підказка: такий ключ потрапляє в чергу перевірки за графіком (одразу, через
добу, 3 доби, тиждень). **Поодинокий запит** виносить вирок, і «знято» він
ставить тільки за явним сигналом (див. «Недоторкане правило»). Відсутність у
видачі не знімає ніколи — і після повного обходу теж.

Одиниця перевірки — ключ «сайт:id» (`listings.site_key`): один запит на
оголошення сайту, вердикт — усім рядкам цього ключа, зокрема копіям LUN. Живе
оголошення, зняте раніше, повертається автоматично з подією «повернулось»
(`listing_events`, попередня дата зняття зберігається), а в строку продажу стає
цензурованим спостереженням. Усі пороги — `config/liveness.toml` (D52).

### Чому не сліпий обхід

Поодинокий обхід усіх 16 тисяч посилань давав повний цикл за 44 дні, а по
трьох джерелах із п'яти — ніколи: черга була спільна й ішла за номером
запису, dom.ria.com займає перші номери, і до решти вона просто не доходила.

Джерела самі перелічують те, що зараз опубліковано, по 20–500 штук за запит:

| джерело | ідентифікаторів | запитів на перелік |
|---|---|---|
| DOM.RIA | 8 539 | **43** (API приймає `limit=500` замість 20) |
| LUN | 5 294 | 223 |
| flombu | 27 | 40 |

**Випадіння зі списку — не доказ зняття.** Оголошення могло опуститись у
ранжуванні або випасти через збій пагінації. Цифра, яка це доводить: у
першому ж прогоні по DOM.RIA з 298 кандидатів **205 виявились живими**.
Сліпе зняття поховало б дві третини з них.

Захист від збою: якщо перелік раптом впав більш ніж на чверть, порівняння
пропускається й логується як помилка. Він одразу спрацював на OLX (2483 → 1119).

**OLX перелічити не можна**: видача жорстко обмежена 25 сторінками — з 26-ї
повертається початок списку (заміряно, `probes/p_olx_depth.py`). Це стеля
близько 1100 оголошень при 2488 у місті, а фільтрів для нарізки видачі в
посиланнях немає. Тому OLX лишається на поодинокій черзі, і саме йому
віддана найбільша порція.

### Що є сигналом на кожному сайті

Заміряно на живій вибірці Етапу 0 (D45): 546 адрес, вердикт — очима й браузером.

| сайт | запит | живе | знято | один 404 |
|---|---|---|---|---|
| dom.ria.com | GET сторінки | 200, стан `active` | 410, або 200 зі станом `archive` **і** банером «Оголошення видалено…» (18 з 18) | «не знайдено» |
| olx.ua | HEAD | 200 (новий slug із тим самим ID — теж) | 410 (222 з 222 збіглися з браузером) | «не знайдено» — загальна сторінка помилки |
| rieltor.ua | HEAD, без www | 200 | 410 (7 з 7) | «не знайдено» |
| lun.ua, flombu.com | HEAD | 200 | лише повторний 404 (нижче) | «не знайдено» |
| blagodeveloper.com | — | — | — | не перевіряється: будь-яка адреса веде на каталог |

HEAD на DOM.RIA сліпий: усі 18 знятих віддавали 200 зі сторінкою «Оголошення
видалено та не бере участі у пошуку». Тому DOM.RIA читається GET і класифікується
за машинним станом сторінки разом із банером; якщо вони розходяться — «не
визначено». Фраза «неактуальн» — кнопка скарги на живих сторінках, не сигнал.
Благо на сайті позначене «актуальність не підтверджена».

### Черги по хостах, а не по джерелах

LUN агрегує OLX: 2 105 його посилань ведуть на olx.ua. Окремі черги «lun» і
«olx» били б в один сайт удвічі частіше за задумане, бо ліміт запитів у сайту
спільний. Черги нарізані по хостах і працюють паралельно — навантаження на
кожен окремий сайт від цього не зростає.

Пауза й порції — свої в кожного сайту (`config/liveness.toml`, розрахунок із
виміряної швидкості зникнення, D52): прогін бере контрольні «відомо живі»
ключі, підказані (відкриті картки, повторні 404, зниклі з переліку, знову
бачені в стрічці), випадкову вибірку знятих і сліпий обхід тих, кому настав
строк.

| сайт | пауза | сліпий обхід за прогін | строк повтору |
|---|---|---|---|
| dom.ria.com | 1.0 с | 45 | 30 діб (головний сигнал — перелік кожні 3 год) |
| rieltor.ua | **3.0 с** | 60 | 4,5 доби (при 1.8 с — 403 після п'яти запитів) |
| olx.ua | 2.0 с | **450** | 2,5 доби (переліку немає) |
| lun.ua | 1.5 с | 5 | 3 доби |
| flombu.com | 1.2 с | 5 | 13 діб |

### Недоторкане правило

**Знімаємо з продажу лише за явним сигналом** (рішення власника, D46): 410,
банер «видалено» на DOM.RIA разом зі станом сторінки, або 404, що повторився
тричі з інтервалом не менше доби, **і** перевірка існування показала, що
оголошення справді немає: повний свіжий перелік пошуку ТОГО САМОГО сайту
(DOM.RIA, LUN, flombu) чи картка DOM.RIA з ознакою видалення. Свіжа стрічка
лише підтверджує, що оголошення є, — «не бачили в стрічці» нічого не доводить
(стрічка OLX обрізана 25 сторінками). Тож OLX (поки адресу лише з ID не
перевірено наживо) і rieltor знімаються тільки за 410. Якщо оголошення є —
лагодимо наше посилання (`listings.probe_url`), а не знімаємо. Один
404, 403, таймаут, обрив мережі, капча, порожня відповідь — це «не
достукались», а не «знято». Одного разу це вже врятувало базу, коли ноутбук
утратив мережу посеред прогону. Після п'яти відмов поспіль черга цього сайту
зупиняється до наступного разу — черги інших сайтів це не чіпає.

**Запобіжник.** Якщо підпис «знято» спрацював на понад 20% перевірених одного
джерела (чи одного сайту — разом із копіями LUN його оголошень) за прогін, для
нього нічого не знімаємо й не повертаємо, у Telegram приходить тривога, і так —
доки власник не зніме запобіжник на `/status` (розділ «Зняті оголошення») чи
`cli.py liveness fuse clear --source …`. Зняття запобіжника — схвалення того, що
він затримав: наступний прогін застосовує ці «знято», не рахуючи їх у частці.
Малі прогони (перевірка при відкритті) рахуються разом із перевірками за останні
3 год. Історія спрацювань і знять — `cli.py liveness fuse status`.

Незрозуміла відповідь ставить `last_attempt`, але **не** `last_checked`: перше
рухає чергу, друге означає «ми справді бачили відповідь» і тримає інтервал для
аналізу виживання. Без цього розділення посилання, яке стабільно віддає 403,
вічно лишалось би першим у черзі — саме так 2 105 записів не перевірились
жодного разу.

### Нічний диригент

Одна команда на одному таймері (`realty-night.timer`, 01:10 і 04:10; D53) робить
усе, що не вміщається в цикл, — під ТИМ САМИМ замком, що й цикл, тож одночасно з
ним не йде ніколи. Вікна й дедлайни — `config/night.toml`: нові запити до 02:47 і
05:47, замок звільнено до 02:55 і 05:55 (цикли — о 03:05 і 06:05).

1. Чекає, поки цикл звільнить замок (раз на хвилину); якщо до 02:47 лишилось менше
   10 хв — вікно пропускає.
2. Якщо останньому успішному бекапу понад 20 год — свіжий бекап із перевіркою
   відновлення. Не вдався — цієї ночі нічого не пише (тривога в Telegram).
3. Кожен сайт — окремий процес-«смуга» у своєму темпі, не швидшому за повний
   збір (`max(delay, full_delay)`: dom.ria.com 1,0 с, olx.ua 2,8 с, rieltor.ua
   3,0 с, lun.ua 1,6 с, flombu.com 1,2 с); сайти паралельно, всередині сайту — по
   черзі за пріоритетом: контрольні «відомо живі» → утримані запобіжником →
   **M2** (зняті старим кодом за одним 404 і «знову бачені» — повертаються лише ті,
   кого перевірка покаже живими) → **M3** (кожен актуальний ключ хоч раз
   перевірений новими підписами; зниклі з переліку — першими) → вибірка знятих →
   догін прострочених → дозбір ознак identity.
4. Раз на ~15 хв диригент застосовує нові результати одним пакетом: спершу
   запобіжник (пакет — це «прогін»), потім запис транзакціями ≤200 рядків з
   подіями. Утримане джерело смуга далі не питає зовсім.
5. О 02:47 смуги зупиняються самі (завислу — примусово), останній пакет, замок
   звільнено, зведення для `/status` і строк продажу «до/після» — у звіт
   `cli.py liveness report`.

Один ключ — не більше одного запиту за ніч. Коли M2 і M3 позаду, вікно — лише
контрольні, вибірка знятих і (якщо прострочених понад 10%) догін: виходить за
хвилини. Блокування (5 відмов поспіль або понад 10%) зупиняють смугу сайту до
кінця ночі; дві ночі поспіль — сайт чекає рішення (`cli.py night unhold --host …`).

### Журнал перевірок

Кожна перевірка пишеться в `check_events` — час, код, вердикт, ярус черги
(контрольна, зникла з переліку, сліпий обхід…) і підпис класифікатора (`alive`,
`status_410`, `ria_archive`, `not_found`, `blocked`…); зняття, повернення й
ремонт посилання — ще й подією в `listing_events` з доказом. Черга навмисно нерівномірна:
вперед ідуть ті, у кого нещодавно впала ціна, і ті, хто давно на ринку.
Нерівномірність зміщує криву виживання, і єдиний спосіб її врахувати — знати
фактичні моменти перевірок. Тому такий порядок без журналу робити не можна.

Разом із `last_alive_at` це дає інтервал, усередині якого оголошення зникло:
точної дати не існує, і вдавати її аналіз не має права.

### Ручна позначка

У таблиці кожен рядок має перемикач:

- **клік** — позначити вручну актуальною або неактуальною;
- **Alt+клік** — зняти позначку й повернути під автоматичне визначення.

Ручне рішення завжди сильніше за автоматичне (`manual_active` перекриває
`is_active`), тож наступна перевірка посилань його не затре. Крапка біля
підпису означає, що стан виставлено людиною.

Фільтр «Актуальність» має три значення: `Актуальні` (типово), `Неактуальні`,
`Усі`. Типово зняті з продажу не показуються й не потрапляють у статистику.

## Сторінка стану системи

`http://127.0.0.1:8000/status` — моніторинг і ручне управління збором.
Оновлюється сама кожні 5 секунд.

- **Фоновий воркер** — `Працює` / `Очікує` / `Не відповідає`, час останнього
  сигналу, лічильник сигналів. Якщо сигналу немає довше за `WORKER_DOWN_MIN`
  (типово 240 хв), сторінка показує тривогу.
- **Джерела** — зібрано, покриття, скільки лишилось, частка успішних запитів,
  блокування за 24 год, час останнього успішного прогону.
- **Якість даних** — оголошення, унікальні квартири, склеєні дублікати,
  скільки ще не пройшло дедуплікацію.
- **Витрати на модель** — виклики, токени, вартість у доларах.
- **Кнопки** — глобальний запуск і окремий для кожного джерела.

Ендпоінти: `GET /api/status`, `GET /api/status/runs`,
`POST /api/status/run` з тілом `{"source": "olx"}` або `{"source": "all"}`.

### Дві речі, важливі для довіри до цифр

**Телеметрія живе в окремій базі** `data/ops.db`, не в `realty.db`. Дані
спостереження за краулером не змішуються з самими оголошеннями: основну базу
можна перебудувати чи перенести, не втративши історії роботи, і навпаки.

**Кнопки запускають окремі процеси** (`cli.py scrape --trigger manual`), а не
виконують збір усередині вебсервера. Помилка збору не може повалити сторінку,
а повторний запуск того самого джерела відхиляється з кодом 409.

Час усюди віддається з явною зоною UTC. Без цього браузер читає мітку як
місцеву — на дашборді моніторингу це давало похибку в кілька годин.

## Про доступ до сайтів

Мережевий шар — це коректний HTTP-клієнт: реалістичні заголовки, ретраї з
